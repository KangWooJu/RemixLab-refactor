PROBLEM 01 일정 산정 및 연동 병목

백엔드 개발 완료 ≠ 전체 기능 완료

  • 백엔드 API 구현 완료 일정 중심으로만 진척도를 판단하여 UX/UI 확정 후 FE 구현·API 연동·통합 테스트 시간을 사전 확보하지 못함.
  • 대응: 핵심 필수 API 우선순위 긴급 재조정 및 데이터 규격 실시간 공유로 릴리즈 방어.
PROBLEM 02 AI 파이프라인 지연 누적

동기식(Blocking) I/O로 인한 스레드 점유

  • GPT, DALL-E, Sora API를 순차적 RestTemplate 동기 호출로 처리.
  • 외부 AI 응답 지연(Latency)이 전체 백엔드 요청 처리 서블릿 스레드를 블로킹하여 파이프라인 전반에 대기 시간이 직접 누적됨.

  • 핵심 비즈니스 로직에 대한 단위/통합 테스트 코드가 부재하여 기능 수정이나 구조 개선 시 기존 동작의 안전성을 검증하기 어려움.
  • 코드 변경에 대한 심리적 장벽 존재.

System Architecture & Security Filter Chain

LAYERED ARCHITECTURE
& SECURITY LIFECYCLE
SECURITY LAYER Spring Security Filter Chain & Request Routing

모든 HTTP 요청은 일차적으로 Security Chain을 거치며, 요청 목적에 따라 전용 필터가 분기 동작합니다.

1. JwtFilter (항상 실행 / Common) Every Request
• 모든 인바운드 요청 헤더의 Access Token 검증 및 SecurityContext에 인증 객체 등록
• 유효하지 않거나 만료된 토큰인 경우 즉시 Security Exception 처리
2. LoginFilter
POST /api/auth/login
로그인 요청 시 인증 수행 후 Access/Refresh Token 동시 발급 ➔ Refresh Token을 Redis에 저장
3. JwtLogoutFilter
POST /api/auth/logout
로그아웃 요청 시 Redis 상의 Refresh Token을 즉시 삭제(Invalidate)하여 토큰 재사용 원천 차단
💡 핵심 구조: 인증 필터 책임을 명확히 분리하여 비즈니스 컨트롤러 진입 전 보안 검증을 완결합니다.
APP CORE 백엔드 레이어드 아키텍처 및 실행 경계
Application Layer CreationFacade (조율) | CreationQueryService (조회)
Non-blocking Reactive Engine WebClient (GPT / DALL-E / Sora 호출)
Execution Boundary publishOn(Schedulers.boundedElastic())
Persistence Layer Spring Data JPA | QueryDSL | Redis Token Store
External Stores & Infra MySQL 8.0 | GCS (Media) | Micrometer + Prometheus
⚡ 경계 분리: 리액티브 Event-Loop 스레드가 Blocking JPA 작업으로 차단되지 않도록 boundedElastic으로 완전히 격리했습니다.

REGRESSION SAFETY
& WEBCLIENT ISOLATION
TEST SAFETY 리팩토링 안정성을 위한 테스트 안전망

외부 AI 및 DB 의존성을 격리하여 구조 변경 시 비즈니스 로직의 회귀(Regression)를 방지했습니다.

  • RefreshService 단위 테스트: Redis 토큰 만료(TTL), 재발급 검증
  • RefreshController Slice 테스트: MockMvc로 400/401 에러 검증
  • AI Orchestration 예외 테스트: 외부 API Timeout 시 비즈니스 예외 전환
🛡 핵심 의도: 단순 커버리지가 아닌 지속적인 아키텍처 리팩토링을 가능하게 하는 안전망을 확보했습니다.
NON-BLOCKING RestTemplate ➔ WebClient + Reactor

외부 AI API 대기 시간 동안 서블릿 스레드가 블로킹되는 문제를 해결하기 위해 리액티브 엔진을 도입했습니다.

  • Non-blocking I/O: I/O 대기 시 스레드 점유 없이 이벤트 루프가 다음 작업 처리
  • 외부 API 관심사 분리: AI 통신/파싱 책임을 전담 클라이언트로 완전 격리
  • 명시적 타임아웃 & 에러 로깅: 장시간 무응답에 대한 Fallback 체계 구축

Long-running Task Lifecycle — Async Video Processing

STATE MACHINE
& BACKGROUND WORKER
PROBLEM & DECISION 영상 생성 생명주기와 HTTP 요청의 분리

영상 렌더링은 수 분 이상 소요되는 대표적인 Long-running Task입니다. 이를 HTTP 요청-응답 주기에 묶어두면 커넥션 타임아웃 및 스레드 풀 고갈이 발생합니다.

  • 즉시 응답 반환: 요청 접수 시 비디오 ID와 PENDING 상태를 즉시 반환하여 클라이언트 연결 종료
  • 스케줄러 & 비동기 워커: 백그라운드에서 주기적으로 외부 Sora AI 상태를 폴링
  • 완료 시 미디어 영속화: 렌더링 완료 감지 시 영상 스트림을 다운로드하여 GCS에 업로드 후 DB 갱신

08 / REFACTORING

Separating Authentication State — Redis Token Store

SECURITY DECOUPLING
& TTL LIFECYCLE
PROBLEM User 도메인과 인증 토큰 상태의 강한 결합

기존에는 Refresh Token 관리 책임이 RDBMS의 User 엔티티에 강하게 결합되어 있어, 토큰 만료 처리나 로그아웃 시 불필요한 RDB I/O 및 도메인 모델 오염이 발생했습니다.

  • 사용자 핵심 도메인 정보와 일시적인 인증 세션 상태의 관심사 혼재
  • 만료된 토큰의 RDB 정리 배치 부담 및 명시적 무효화(Blacklisting) 복잡성
DECISION Redis 기반 독립 Refresh Token 생명주기 관리
  • 도메인 책임 분리: User 엔티티에서 토큰 상태를 완전히 제거하고 Redis로 전담 격리
  • TTL 기반 자동 만료: Redis Expire Time(TTL)을 활용해 만료 토큰을 배치 없이 자동 파기
  • 명시적 무효화 (Logout): 로그아웃 요청 시 Redis 키를 즉시 삭제하여 접근 차단
🔑 포커스: 성능 향상이 목적이 아닌, 책임의 분리(Separation of Concerns)와 안전한 토큰 생명주기 제어에 집중했습니다.

RESPONSIBILITY 비대해진 Service 계층의 책임 세분화

단일 Service에 비즈니스 검증, 외부 AI 오케스트레이션, DB 영속화, 동적 조회가 집중되는 문제를 해결하기 위해 Facade 패턴과 CQRS 관점의 Query Service 분리를 적용했습니다.

[COMMAND FLOW] CREATION & MUTATION
Controller: 요청 수신 및 응답 매핑
↓
CreationFacade: AI 오케스트레이션 흐름 조율

Domain Service: 순수 비즈니스 룰 검증
↓
Persistence Facade / JPA: 영속화 처리

Controller: 검색/조회 파라미터 수신
↓
CreationQueryService: 읽기 전용 트랜잭션 (readOnly=true)
↓
QueryDSL Custom Repository: 동적 필터링 및 DTO 직접 프로젝션

01. Architecture

기술을 추가하기 전 I/O와 CPU 바운드 특성을 구분하고 실행 환경에 적합한 구조를 선택해야 함을 배웠습니다.

02. Async Lifecycle

비동기 처리는 단순 라이브러리 사용이 아닌 장시간 작업의 상태 머신과 장애 복구 생명주기를 관리하는 것입니다.

03. Verification & Safety

테스트와 메트릭은 단순 절차가 아닌, 리팩토링을 두려움 없이 지속하게 돕는 안전망임을 체감했습니다.

04. Collaboration

백엔드 API는 코드 작성이 끝나는 시점이 아니라 클라이언트가 온전히 연동·검증했을 때 완성됩니다.
